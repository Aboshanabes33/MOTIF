# Can MOTIF reuse an existing Codex CLI sign-in?

**PARTIALLY.** No documented session bridge was found from an already signed-in Codex CLI to MOTIF’s pinned Pi runtime. A local process can instead ask **Codex itself** to report its account, list models and run a turn. That uses a supported interface without giving Pi or MOTIF the credential. It tests the desired *experience*, not Pi-native OAuth reuse. **Real authenticated inference was not proven in this checkout.**

## What was inspected before building the probe

- Baseline `c105107`: a browser UI with TanStack Start server functions. There is no Electron host on the user's machine. `src/lib/account-link.functions.ts` resolves a signed browser principal on the server. `src/lib/connection-vault.server.ts` holds its encrypted credentials. A subprocess started there would see the **server's** Codex profile.
- `src/lib/provider-registry.ts`: API keys for OpenAI, Anthropic, Gemini, xAI, OpenRouter and OpenCode Zen/Go; OpenRouter BYOAI sign-in mints an API key. Codex is hidden; Copilot OAuth is not enabled. No provider or UI changed in this experiment.
- `package.json` and the lockfile pin `@earendil-works/pi-ai` and `@earendil-works/pi-coding-agent` to **1.5.2**. No `node_modules` was initially present, so the exact published packages were unpacked outside the project, not upgraded. `src/lib/pi.server.ts` supplies an owner-scoped `CredentialStore` to `ModelRuntime.create`, checks for a stored API key, and returns a completed text result via `completeSimple`. It does not spawn Codex, stream to the browser, or create an agent session.
- In the **[pi-ai 1.5.2 package](https://www.npmjs.com/package/@earendil-works/pi-ai/v/1.5.2)**, `dist/providers/openai-codex.js` registers its own OAuth subscription provider with a Pi model catalogue and a Codex Responses transport. `dist/auth/oauth/openai-codex.js` implements login and refresh. `dist/auth/resolve.js` refreshes expiring stored OAuth credentials through the supplied credential store. In **[pi-coding-agent 1.5.2](https://www.npmjs.com/package/@earendil-works/pi-coding-agent/v/1.5.2)**, `dist/core/model-runtime.d.ts` exposes `getModels`, `listCredentials`, `login`, `getAuth` and `streamSimple`. A listed model is not evidence of a valid session or entitlement.
- Neither the inspected implementations nor the [Pi providers](https://docs.pi.dev/latest/providers) and [SDK](https://docs.pi.dev/latest/sdk) guides identified a credential-free handle to Codex’s existing login. Pi’s normal interactive login stores a **Pi** credential. A custom Pi credential store that reads Codex tokens would not be a token-free bridge; it would also introduce a second owner of refresh/rotation. This POC does not implement that adapter or import authentication files.

## Local test (Node 22+, trusted Codex CLI on PATH)

Run **on the machine and OS account where you use Codex**, in a trusted CLI profile configured for the official OpenAI service. Do not run this in a hosted MOTIF process. No MOTIF dependencies or `.env` needed.

```sh
node poc/codex-session/probe.mjs                # metadata only; no login, prompt or explicit refresh
node poc/codex-session/probe.mjs --list         # list non-hidden model names from Codex
node poc/codex-session/probe.mjs --send MODEL   # replace MODEL with one listed name; uses quota
node --test poc/codex-session/probe.test.mjs    # offline protocol fixtures; no CLI needed
```

If the CLI is missing, follow the [official Codex CLI install guide](https://developers.openai.com/codex/cli) (for example `npm install -g @openai/codex`). If signed out, run `codex login` yourself and choose ChatGPT in the official browser flow; headless environments may support `codex login --device-auth` if enabled by the account/workspace. API-key login is separate and deliberately does **not** pass this POC. The probe does not install anything, sign you out, switch accounts or initiate login. A cached session can still fail on the next request; it does not guarantee a particular plan, remaining quota, or model access.

[Codex authentication](https://developers.openai.com/codex/auth) describes the CLI's local cache (`auth.json` in Codex home, typically `~/.codex`, or an OS credential store depending on configuration). The probe never opens either store. Only Codex manages its session and communicates with its provider. It receives a minimal environment without API-key/token overrides. Use a trusted local executable and configuration: this is not a sandbox for an untrusted binary or plugins.

## Protocol and results

The [maintained App Server contract](https://developers.openai.com/codex/app-server) and [source](https://github.com/openai/codex/tree/main/codex-rs/app-server) describe JSONL over stdio. Checked against schemas generated by `codex-cli 0.171.0`. Handshake → `account/read` (no requested refresh) → `model/list` with pagination → explicit model → ephemeral `thread/start` → one fixed `turn/start`. Only `item/agentMessage/delta` for that thread/turn is rendered, restricted to the expected literal `PONG` to avoid printing arbitrary output. Success requires a matching `turn/completed` with completed status. No raw protocol logs, account identity, child stderr, pasted tokens, custom prompts or approval handling. No listening socket or product backend.

| Check | Actual result |
|---|---|
| Original sandbox PATH | CLI not found; diagnostic exit 1. This says nothing about the user's laptop. |
| Official `@openai/codex@0.171.0` installed in a disposable prefix, empty home | Real stdio initialize and `account/read` worked; signed out; exit 2, no inference sent. No existing user credential was read or transferred by the probe. |
| Offline fixtures | Six tests passed: signed-out/API-key refusal, status/list separation, pagination, model selection, matching streamed deltas, terminal success/failure and output filtering. |
| Existing authenticated device, live catalogue, streamed inference or actual refresh | **Not tested.** No authorized signed-in ChatGPT session was available here. Fixtures and signed-out RPC success do not prove any of these. A user on an eligible local deployment can run `--list` and `--send` above. Report only CLI version, model and success/failure, never auth files or logs. |

## Architecture decision

Keep the existing hosted Pi providers untouched. OpenAI’s [App Server authentication guidance](https://developers.openai.com/codex/app-server) distinguishes local/open-source clients from commercial or hosted services, and recommends Sign in with ChatGPT. Do not use CLI-managed auth to fund a hosted MOTIF service. For hosted subscription inference, pursue MOTIF's own approved [Sign in with ChatGPT plan integration](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt); account identity alone is insufficient.

Only after a successful authorized **local** live test and eligibility review: consider a separately distributed opt-in local adapter to the existing provider boundary, using App Server for metadata, model selection and text streaming, keeping prompts/credentials local to the client and intended provider. Do not present this as the Pi `openai-codex` adapter or ship it as a web endpoint. Before rollout, test cancellation, expired/revoked accounts, rate limits, stale model lists, version compatibility, and independence of all existing hosted provider paths.
